Context / 01

Zenisth IDP is the AI-powered document intelligence layer of the Zenisth platform. It extracts structured data from unstructured documents invoices, contracts, reports at enterprise scale.

My job was not to design screens. It was to design a system that non-technical operations teams could trust predictable, auditable, and cost-transparent.

Design Principles / 02

4 rules I defined before touching a frame.

01
Consent Before Compute

Users must see what will happen and what it costs before the system acts. No silent processing.

02
Simple Before Smart

A workflow that non-technical users can operate confidently beats a smart one that confuses them.

03
Reusable Before Repeatable

Configuration built once and reused is better than configuration rebuilt every time.

04
Trust Over Automation Hype

Enterprise teams need to trust the system first. Automation value comes after trust is earned.

The Problem / 03

Operations teams were doing manually
what machines should be doing reliably.

01
Manual Data Entry

Teams were re-keying invoice data, contract terms, and report values — spending hours on work that should take seconds.

02
Rechecking AI Outputs

Existing tools produced unpredictable extractions. Every result required manual verification — erasing the automation benefit.

03
Hidden Processing Costs

LLM + OCR costs were invisible until after processing. Billing surprises created distrust and slowed enterprise adoption.

04
Inconsistent Extraction

Without standardized schemas, same-type documents produced different structures. Downstream systems broke constantly.

Core Design Thesis

Existing tools were complex, unpredictable, and over-engineered for the people who needed them most. I designed IDP to be a controlled extraction system not an AI demo. Simple. Predictable. Enterprise-safe.

Design Decisions / 04

7 decisions across 7 modules. Each one made under real constraints time pressure, developer capacity, and enterprise user expectations. Every decision traces back to one of the 4 principles.

Module 1 — Upload & Ingestion
01
Upload
Document Preview Before Processing

Processing the moment a file lands is fast for the machine and expensive for the user who uploaded the wrong batch.

I introduced a staging area between upload and processing. Users can review every document, remove incorrect files, and add missed ones all before a single credit is spent. This isn't just a UX nicety; it eliminates a whole category of support tickets ("I uploaded the wrong file") and prevents wasted compute on the backend.

Rejected — Process Immediately

Upload triggers processing instantly. Wrong files waste credits. Re-runs are required. Frustration compounds.

Chosen — Staging Area

Upload lands in preview. User confirms the batch. Only then does processing begin. Full control maintained.

User Impact
Fewer errors before extraction
No wasted credits on wrong files
Confidence in what will be processed
Dev Impact
Cleaner processing queue
Fewer reruns needed
Lower backend compute waste
Business Impact
Lower OCR cost per run
Fewer support tickets
Higher enterprise trust
Consent Before Compute no action before user confirms
Module 2 — Tag-Based Schema System
02
Schema
Reusable Tags Instead of Per-Run Prompts

Asking teams to reconfigure extraction logic every batch is not a workflow it's a recurring tax on their attention.

A Tag is a saved extraction schema template it bundles the fields to extract, the document type, and the output format. Define it once, reuse it across every batch. No reconfiguration. No guesswork. The extraction model behaves consistently because the input schema is consistent. Enterprise teams get standardized output by default, not by luck.

User Impact
No reconfiguration per batch
Faster operations at scale
Predictable extraction output
Dev Impact
Structured schema storage
Clear field-mapping logic
Easier backend validation
Business Impact
Cross-department standardization
Enterprise scalability
Downstream system stability
Reusable Before Repeatable configure once, use everywhere
Module 3 — Credit Transparency
03
Trust System
Estimated Credits Shown Before Extraction

LLM + OCR costs real money. Hidden processing creates distrust. And distrust, in enterprise SaaS, is a churn event.

I designed a Batch Summary screen that sits between configuration and execution. It shows: the number of documents detected, estimated credit cost, and a clear confirmation button. Users see what they're about to spend before they spend it. This is not just UX it's a product-level trust contract. Procurement teams can budget. Finance can audit. Operations can act without fear.

Without Transparency

Processing starts, credits deduct, user discovers the cost after the fact. Dispute raised. Support ticket opened. Trust broken.

With Batch Summary

User sees document count + estimated credits before confirming. Full budget control. No surprises. Confidence gained.

User Impact
No surprise billing
Full budget control
Dev Impact
Clear cost computation logic
Predictable API triggers
Business Impact
Fewer billing disputes
Higher enterprise adoption
Consent Before Compute no spend without user confirmation
Module 4 — Classification Removal (V1)
04
Scope Cut
Remove Classification in V1

Automatic document classification sounds like smart product thinking. In V1, it was a complexity trap.

Auto-classification increased cognitive load for users who needed to understand and trust what the system was doing. It multiplied edge cases, made credit calculation harder to explain, and slowed development. The tradeoff was clear: remove the automation layer, ship a reliable extraction core, and validate that first. Classification moves to V2 when we have usage data to justify it.

User Impact
Simpler onboarding experience
Faster learning curve
Dev Impact
Faster shipping timeline
Reduced backend branching
Business Impact
Faster go-to-market
Lower infrastructure cost
Simple Before Smart reliability before automation
Module 5 — Review Queue Removal (V1)
05
Scope Cut
Remove Manual Review Flow

A review queue is a powerful enterprise feature. It is also a V1 scope killer if the extraction engine it reviews isn't trusted yet.

Manual review adds: complex UI states, human-in-the-loop coordination logic, assignment and notification systems, and significant state management overhead. V1's goal was to validate extraction reliability not to build a review workflow. Once the extraction is trusted, the review layer has a reason to exist. Not before.

User Impact
Faster processing flow
Less cognitive overhead
Dev Impact
Fewer UI states to handle
Cleaner API responses
Business Impact
Reduced development cycle
Lower maintenance burden
Module 6 — Output Format
06
Schema
Export Format Defined in Tag, Not at Download

Asking users to pick a download format at the end of a long process is a small friction point with a large psychological cost.

Output format is defined once during Tag creation not at the moment of download. This eliminates decision fatigue at the worst possible moment (post-extraction, when users just want their data). It also means the export pipeline handles one format per batch, simplifying the transformation logic significantly. Predictable in → predictable out.

User Impact
Predictable download results
No decision fatigue at end
Dev Impact
Single format transformation logic
Simplified export pipeline
Business Impact
Cleaner architecture
Reduced edge cases
Simple Before Smart fewer choices at critical moments
Module 7 — Design System
07
Design System
Token-Based Design System for the Entire Platform

Zenisth has 6 tools. A design system built only for IDP is a dead end. A token-based system is a platform asset.

I built a token-based design system with base tokens (colors, spacing, typography), semantic tokens (success, warning, error states), shared components, and reusable layout patterns. Every component built for IDP is available to Transify, Voice, and every future tool without restyling or duplication. This decision compounded in value with every tool shipped after it.

User Impact
Consistent experience across tools
Lower learning curve per tool
Unified mental model
Dev Impact
Faster UI implementation per tool
Reusable component logic
Reduced UI bugs across platform
Business Impact
Faster feature delivery
Scalable platform growth
Brand consistency at scale
Reusable Before Repeatable build once, scale everywhere

Edge Case Thinking / 06

Every system breaks.
I designed for when it does.

These aren't afterthoughts they're first-class design decisions. Handling edge cases is what separates enterprise-grade from demo-grade.

📄
Duplicate Uploads
Preview stage flags duplicates before processing. User decides no silent deduplication.
⚠️
Corrupted Documents
Clear failure state with reason, retry option, and file safety confirmation. No red error walls.
🔄
Partial Extraction Failures
Partial success reported clearly. Successfully extracted documents downloadable immediately.
📦
Large Batch Processing
Batch summary credit estimate scales with volume. Users see cost before committing large batches.
🧮
Credit Miscalculation
Estimates are shown as "up to X credits" conservative framing prevents underbilling surprises.
🔀
Schema Mismatch
When document type doesn't match Tag schema, extraction reports field-level gaps not silent failures.
📏
Document Size Limits
Size limits communicated at upload, not after processing. Users know before they commit.
🧑‍💼
Non-Technical User Confusion
Plain-language microcopy at every step. No technical error codes in user-facing interfaces.
🏢
Enterprise Governance
Confirmation events and Document History provide audit-ready logs for compliance teams.
