Context / 01

Zenisth AI is a B2B SaaS platform with multiple tools built for handling enterprise documents. Transify is the translation tool within this system. It works alongside other tools like IDP and Voice, all connected under one shared platform. I led the end-to-end design of Transify.

My role was not just designing screens I defined how the workflow works, how credits are calculated, how tags are structured, and how the experience stays consistent across the platform.

Every design decision had to balance three things:

  • What makes sense for the user
  • What works for the business
  • What is practical for developers to build

The Problem / 02

Enterprise translation tools behave like utilities,
not workflows.

01

Inconsistent terminology across teams. No system to enforce standard language.

02

No batch control. Users submit documents without understanding cost or scope.

03

Unclear cost estimation leads to billing surprises and loss of trust.

04

Formatting is often lost. Translated documents require manual reconstruction.

05

Manual coordination across teams. No unified view of document lifecycle.

06

Tool fragmentation. Separate histories and configurations across tools create confusion.

Core Design Thesis

Transify was built as a predictable workflow layer within the platform not as a standalone AI utility.

For enterprise teams, reliability and cost clarity matter as much as translation accuracy.

Design Decisions / 04

Every decision below was made under real constraints time pressure, developer dependencies, and enterprise user expectations. Here's the reasoning behind each one.

01
Architecture
Step-Based Workflow Instead of Single Page

A single-page translation interface is faster to build, but harder to operate at enterprise scale. When multiple configuration options, document controls, and cost indicators appear at once, users face decision friction and higher error risk.

I structured the workflow into four explicit states: Upload ? Select Tag ? Translate ? Download. Each step isolates one cognitive task. Users complete and commit before moving forward. This mirrors backend state transitions, enabling cleaner API contracts, better error handling per step, and clearer audit logs.

Rejected

Single-page interface with all options visible simultaneously difficult to manage state, harder to recover from partial failures.

Chosen

Linear step-based workflow with explicit progress indicators users always know where they are, what�s next, and what has been committed.

UX Impact
Lower configuration mistakes
Faster onboarding for new enterprise users
Clearer mental model across tools (IDP alignment)
Dev Impact
Clean state-based logic
Easier failure isolation per step
Predictable backend transitions
Hick's Law: Reduce choices at every decision point
02
Architecture
Tag System: Reusable Translation Configurations

Letting users enter free-form prompts every time creates unpredictable output and decision fatigue at enterprise scale.

Tags are saved configurations that bundle: source language, target language, glossary, category, and description. A team creates a Tag once, and reuses it across every translation eliminating variance, enforcing brand terminology, and enabling non-technical users to operate with confidence.

Business Impact
Standardized output across teams
Lower error rate per translation batch
Brand consistency at scale
Dev Impact
Config-driven architecture
Reduced runtime variability
Clean schema storage
Progressive Disclosure: hide complexity, surface control
03
Trust System
Confirmation-Based Credit Deduction

Enterprise buyers have been burned by hidden charges. The moment trust breaks, they churn and they bring procurement teams to the cancellation meeting.

Credits are not deducted on upload. Not during processing. Not during preview. Credits are deducted only when the user clicks "Next" to confirm. This is not just a UX nicety it is a trust contract written in product behavior. The microcopy mirrors this: "Credits will be deducted only after you confirm."

What Competitors Do

Deduct on upload or on start of processing users discover charges after the fact, creating disputes and anxiety.

Transify Approach

Explicit confirmation moment: users see cost before committing, maintaining complete control of spend.

Trust Impact
Reduced billing disputes
Stronger onboarding confidence
Sales Impact
Easier procurement approval
Clear audit trail for finance teams
Loss Aversion: make cost visible before loss occurs
04
Pricing UX
Flat Upload Cost (V1)

Variable upload pricing forces users to calculate before they act. That friction is enough to pause a workflow indefinitely.

V1 uses a flat 2-credit upload cost regardless of document count. Simple. Predictable. No mental arithmetic required before starting. This decision trades pricing granularity for cognitive speed the right tradeoff at the validation stage.

Cognitive Impact
Instant clarity no calculation needed
Lower decision friction at start of workflow
Business Trade-off
Less pricing granularity (post-V1 refinement)
Simpler to explain to enterprise buyers
05
Pricing UX
Character-Based Translation Cost Formula

Pricing per translation job is a black box. Enterprise teams need to forecast spend they cannot budget against mystery numbers.

After evaluating per-10,000 and per-1,000 character models, I landed on: 1,000 characters = 5 credits. This formula is simple enough to calculate mentally, prominent in the batch summary UI, and precise enough to build budget forecasts around. Transparency here is not just good UX it's a sales asset.

Pricing Clarity
Predictable cost per document type
Fewer billing questions to support
Sales Alignment
CFOs can model usage costs upfront
Reduces objections in enterprise deals
06
Platform Architecture
Document History (Not Translation History)

Separate histories for each tool Translation, Extraction, Upload creates fragmented audit trails that break at enterprise scale.

I unified all events into a single Document History model. This was a platform-level decision, not a UI decoration. One document can flow through IDP, Transify, and Voice the history captures all of it. Enterprise clients need audit readiness. Legal teams need document lifecycle logs. This architecture provides both, without extra engineering overhead per tool.

Platform Impact
Future-proof multi-tool architecture
Easier expansion to Voice and beyond
Enterprise Value
Audit-ready document lifecycle logs
Cross-tool visibility in one view
07
UX Resilience
Smart Failure States

A red error screen at a critical processing moment panics enterprise users and triggers immediate support tickets.

Every failure state includes: a plain-language reason (no technical codes), a retry button, a re-upload option, and a message confirming files are safe. The design principle is: never blame the user, never leave them stranded. Recovery paths must be as prominent as the failure message itself.

UX Impact
Reduced panic at failure moments
Maintained workflow momentum
Support Impact
Fewer "my document is gone" tickets
Self-serve recovery reduces load
Error Recovery: give users a path forward, not a dead end
08
Safety UX
Confirmation Modals for Destructive Actions

In enterprise tools, an accidental delete is not an inconvenience it's an incident report.

Delete Tag, Cancel Translation, and Cancel Upload all require explicit confirmation. No silent destructive actions. This pattern communicates respect for the user's work and the organization's data. The cost of one extra click is nothing compared to the cost of irreversible data loss in an enterprise context.

Trust Impact
Enterprise tools must feel safe to operate
Reduces accidental data loss
Compliance Impact
Traceable confirmation events
Supports audit requirements
09
Product Strategy
V1 Scope Reduction: What I Removed

The strongest signal of product maturity is knowing what to cut. Not what to build what to protect the launch from.

Features removed for V1: prompt instructions, manual correction flow, reviewer queue, Tag Library analytics, comments system. Each of these is valuable but each also adds surface area that slows validation. V1 tests the core loop: Can enterprise users translate documents reliably, with predictable cost, in a controlled workflow? Everything else is V2.

Launch Speed
Focused scope enables faster shipping
Core loop validated without noise
Strategic Gain
V2 roadmap already clear
No over-engineering sunk cost
10
Design System
Reusable UI Components Across Tools

A design system that only serves one tool is a liability. One that scales across all tools is a competitive moat.

The Tag Card component, Batch Summary, and Navigation are built once and shared across Transify, IDP, and future tools. This decision saved development time on every subsequent tool, maintained brand consistency without enforcing it manually, and created a unified state-handling model that developers could rely on platform-wide.

Dev Impact
Reduced component duplication
Faster UI implementation per tool
Brand Impact
Cross-tool visual consistency
Unified user mental model
